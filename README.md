# Agentic Sim

Agentic Sim implements Phase 1 (PR1–PR3) and Phase 1.5 (PR4) of the
[implementation plan](docs/IMPLEMENTATION_PLAN.md). It is a deterministic,
typed Python discrete-event simulator for synthetic multi-turn inference on a
coarse prefill/decode-disaggregated system.

## Implemented scope

- deterministic event execution and seeded synthetic workloads;
- multi-turn agents, context growth, tool waits, and configurable KV retention;
- dynamic FCFS whole-prompt prefill batching;
- independent per-session P-to-D KV ingress, optionally sharing system bandwidth;
- iteration-level continuous decode batching with boundary admission/removal;
- generic memory and directed latency-plus-bandwidth links for KV restore/store;
- request, batching, TTFT, inter-token, queue, bandwidth, throughput, and resource metrics;
- backward compatibility with Phase 1 flat compute-rate configurations.

The implementation intentionally excludes sweeps, decode epoch coalescing,
xPU/NMP models, MoE, advanced scheduling, detailed/passive optical fabric
models, trace input, and ASTRA-Sim integration.

## Execution model

```text
optional retained-KV restore
  -> prefill queue -> dynamic whole-prompt batch
  -> independent per-session P-to-D ingress
  -> decode waiting queue -> continuous decode iterations
```

Prefill greedily packs the FCFS head subject to request and token limits. An
oversized head runs alone, and Phase 1.5 adds no batch-formation delay. For a
packed batch:

```text
T_prefill = fixed_latency + max(
  longest_prompt / single_request_rate,
  total_batch_tokens / system_rate
)
```

With `B` active decode sessions, one iteration emits one token per session:

```text
T_decode_step = fixed_latency + max(
  1 / single_session_rate,
  B / system_rate
)
```

Sessions enter and leave the active decode set only at iteration boundaries.
There is one `DECODE_STEP_FINISH` event per iteration; epoch coalescing is not
implemented.

When `hardware.kv_ingress` is configured, flows first incur fixed latency and
then share bandwidth equally. With `N` active flows:

```text
flow_bandwidth = min(per_session_cap, system_cap / N)
```

Each flow completes independently and makes only its own session decode-ready.
Without this block, legacy configurations continue using the Phase 1 direct
P-to-D link.

## Workload token semantics

`workload.context_tokens` optionally defines the complete first-turn prompt.
When present, it is sampled once per agent. `workload.input_tokens` is then
sampled only for turns 2 through N and represents newly returned tool/API data.
`workload.output_tokens` is sampled for every turn and is generated by decode.

For constant values and `N` turns:

```text
new prompt/input tokens = context_tokens + (N - 1) * input_tokens
generated tokens        = N * output_tokens
final context           = context_tokens
                        + (N - 1) * input_tokens
                        + N * output_tokens
```

If `context_tokens` is omitted, legacy configurations remain valid and
`input_tokens` supplies every turn's prompt, including turn 1.

## KV retention

`invocation_model.kv.retention` is globally `same_device`, `memory`,
`far_memory`, or `discard`. All retained modes prefill only new turn input.

- `same_device` assumes prior KV remains resident and reusable on the prefill
  device. It creates no store, memory-read, or restore tasks and needs no KV
  memory resource or retention links. P and D remain distinct, and normal P-to-D
  prompt-KV ingress still occurs. Any coherence of decode-produced KV back to P
  is assumed zero-cost; prefill-device KV capacity is not modeled.
- `memory` and `far_memory` store KV after non-final decode and restore it before
  the next prefill. Storage overlaps tool wait and can produce `KV_WAIT`.
- `discard` stores nothing and recomputes prior context plus new input.

Final-turn KV is never stored. KV byte sizes remain token count times
`kv.bytes_per_token`.

## Configuration

Preferred Phase 1.5 compute and ingress configuration:

```yaml
hardware:
  devices:
    - id: 0
      class: compute
      fixed_latency_us: 5
      prefill:
        single_request_tokens_per_second: 18000
        max_system_tokens_per_second: 72000
        max_batch_requests: 16
        max_batch_tokens: 65536
        layout: packed
        batch_wait_us: 0
    - id: 1
      class: compute
      fixed_latency_us: 5
      decode:
        single_session_tokens_per_second: 50
        max_system_tokens_per_second: 2500
        max_active_sessions: 256
  kv_ingress:
    fixed_latency_us: 2
    per_session_max_bandwidth_bytes_per_sec: 2.0e11
    max_system_bandwidth_bytes_per_sec: 8.0e11
```

Legacy devices declaring `prefill_tokens_per_second` and
`decode_tokens_per_second` remain valid. They normalize to equal single/system
rates, `max_batch_requests: 1`, and `max_active_sessions: 1`; ingress continues
to use the configured direct P-to-D link.

`memory` and `far_memory` modes additionally require D-to-selected-memory and
selected-memory-to-P links. Memory capacity is descriptive in this phase;
allocation, eviction, and placement optimization are not modeled.

## Architecture

```text
YAML -> seeded WorkloadGenerator -> AgenticRuntime
                                  -> PrefillBatchController
                                  -> KVIngressController
                                  -> DecodeBatchController
                                  -> TaskBuilder + static placement
      -> EventEngine -> SimpleHardwareBackend -> MetricsCollector
```

The event engine contains no workload or hardware-specific logic. Controller
state is explicit so later batching policies or epoch coalescing can extend the
runtime without rewriting the engine. Restore/store continue through generic,
hardware-independent tasks and the simple backend.

## Run

Python 3.11 or newer is required.

```bash
python3 -m venv .venv
.venv/bin/pip install -e '.[test]'
.venv/bin/pytest
.venv/bin/python examples/run_simulation.py
```

The example prints the in-memory system summary, per-agent metrics (including
the sums of all prefill- and decode-stage durations), and per-resource metrics. See
[the Phase 1 implementation summary](docs/implementation_summary.md) for the
implemented assumptions, verified example results, and deferred work. See the
[output metrics reference](docs/metrics_reference.md) for detailed definitions,
units, formulas, populations, and interpretation guidance.
